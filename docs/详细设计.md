# FFmpeg 静止画面剪切器——详细设计

## 1. 设计目标

本文将系统设计拆解为可直接编码的类、接口、状态、IPC、算法和 FFmpeg 命令生成规则。

## 2. 技术选型

- Electron：桌面容器、文件系统和系统对话框。
- React + TypeScript：界面和强类型业务逻辑。
- Vite：构建。
- Zustand：轻量全局状态。

## 7. MediaProbe 详细设计

命令：

```bash
ffprobe -v error -print_format json -show_format -show_streams input.mp4
```

解析规则：

- duration 优先 `format.duration`。
- 找第一条 `codec_type=video` 的 stream。
- 音频存在任意 `codec_type=audio` 即 `hasAudio=true`。
- fps 从 `avg_frame_rate` 解析；若无效再尝试 `r_frame_rate`。
- duration 必须 > 0。

错误条件：

- ffprobe 非 0。
- JSON 无法解析。
- 无 video stream。
- duration 非法。

### 8.2 长视频自适应检测

30 秒以上视频不再对整段原始帧流直接执行完整 `freezedetect`，而是采用两阶段策略：

1. 快速粗扫：缩放到 360p，并根据最短静止时长动态选择 1–8 FPS；默认 2 秒阈值使用 2 FPS。
2. 原分辨率精修：粗扫只产生候选，最终边界仍回到原分辨率确认。

为降低候选密集型超长视频的精修成本：

- 每个候选只生成“开始边界窗口”和“结束边界窗口”，不会重新解码整个静止段。
- 相邻/重叠边界窗口会自动合并，单个合并窗口最长 12 秒，避免合并过大导致重新大量解码。
- 合并后的精修窗口最多 4 路并行执行。
- 同一候选至少有一个边界必须被原分辨率检测确认，否则视为粗扫假阳性并丢弃。
- 精确边界采用一对一匹配，同一个原分辨率边界不会同时确认多个相邻粗候选。
- 精修后若区间发生真实重叠，则合并去重；仅首尾相接但不重叠的独立区间保持分离。
- 共享同一个 AbortSignal；取消检测时所有正在运行的精修进程会一起终止。
- 真实基准 `0121-1.mp4`：优化前 755.139 秒；合并窗口 + 4 路并行 + 匹配保护后 315.879 秒，约缩短 58%。

实测基准文件 `C:\Users\asus\Desktop\hxsd-一阶段\0121-1.mp4`（约 5.32 GB、8:22:20、1080p、约 30 FPS）用于长期性能回归。

### 8.3 手动定向检测

导入 MP4 后不再自动启动静止检测。播放器只负责加载媒体并显示当前时间点，用户完成参数设置后手动点击“启动检测”。

检测请求包含：

- 当前播放器时间 `currentTimeSec`
- 检测方向：`forward` / `backward`
- 最大返回区间数量 `maxIntervals`
- 最短静止时长
- 允许画面变化阈值
- 是否有背景声音
- 视频是否存在音轨

定向搜索采用自适应分块 + Lazy Refinement：

1. 从当前时间点开始按 `30 → 60 → 120 → 300` 秒递增扫描块；进入第 4 个块后继续使用 300 秒上限，附近已有结果时不再预先扫描完整 5 分钟。
2. 向后检测时按时间增加方向继续扫描；向前检测时按时间减少方向扫描，每个新块只推进未搜索区域，同时保留少量重叠上下文。
3. 每个块仍使用“低 FPS / 360p 粗扫 + 原分辨率边界精修”，但粗扫得到的候选先按距播放头远近排序。
4. Lazy Refinement 首批只精修 `maxIntervals + 2` 个最近候选（且不少于 4 个）；若精修失败、静音筛选后数量不足，再继续精修后续候选，不再对整块几十个粗候选一次性全部精修。
5. 边界精修必须同时确认同一候选的 `start` 和 `end`；任何一侧未找到精确边界时丢弃该候选，不把粗扫边界混入最终结果。
6. “无背景声音”模式下，同一块的视觉粗扫与音频 `silencedetect` 并行执行；先用静音区间对粗候选做宽容预筛，再仅精修可能形成静音交集的候选。
7. 定向视觉粗扫与静音扫描使用基于 `path + size + mtime` 的 64 项 LRU 内存缓存；文件内容变化后自动形成新 cache identity，避免复用旧文件结果。
8. 找到用户指定数量后立即停止；触及尚未扫描边界的候选仍延迟到下一重叠块确认，防止把块边界当成真实 freeze_end / freeze_start。

背景声音规则：

- “有背景声音”开启：静止判断只看画面，不要求音频静默。
- “有背景声音”关闭且视频存在音轨：使用 `silencedetect=noise=-35dB` 检测静音段，然后返回 **视觉静止区间 ∩ 音频静音区间** 的连续交集。
- 每个交集区间必须再次满足“最短静止时长”；一个视觉静止区间内若存在多个足够长的静音段，可以拆成多个候选。
- 不再因为“整段视觉静止区间里存在至少一小段静音”而保留整段，从而保证返回候选的起止范围本身都满足静音条件。
- 无音轨视频：无论该开关状态如何，都只按画面判断。

真实基准 `C:\Users\asus\Desktop\hxsd-一阶段\0121-1.mp4`：
从 04:00:00 开始向后查找 3 个静止区间，完成时间约 4.731 秒。

2026-10-09 使用 `0122.mp4` 在约 05:15:45 位置回归：
- 画面静止模式前三个精修区间起点分别为 18948.9333、18953.699967、18958.899967 秒，与直接全帧 `freezedetect` 对照一致。
- “无背景声音”模式返回的第一个静音交集为 18983.292979 → 18985.978083 秒（约 2.685104 秒），不再返回原先包含有声部分的约 32 秒视觉静止整段。

### 8.4 当前画面相似定位

该功能与“方向查找静止区间”并行存在，不替代原有快速检测。

目标：以播放器当前时间点对应的画面作为锚点，允许用户配置画面变化等级，然后向左右定位持续满足该等级的最大连续父区间。

变化等级：

| 等级 | 最大标准化平均像素差 | 用途 |
| --- | ---: | --- |
| 严格 | 0% | 原始解码像素完全一致，保留旧 MD5 行为 |
| 极低 | 0.005% | 只容忍极轻微压缩抖动 |
| 低 | 0.02% | 容忍少量编码噪声 |
| 标准 | 0.05% | 默认，兼顾稳定性和实用区间长度 |
| 宽松 | 0.08% | 允许更明显的小范围画面变化 |
| 很宽松 | 0.10% | 适合压缩噪声大或缓慢变化的素材 |

“标准化平均像素差”计算方式：

1. 当前锚点帧和待比较帧统一缩放到 160×90。
2. 转为 8-bit 灰度图。
3. 对每个像素计算绝对差。
4. 使用 `sum(abs(anchor - frame)) / (pixelCount * 255)` 得到 0～1 的差异值。
5. 差异值不超过当前等级阈值即认为该帧与当前画面相似。

实现策略：

- “严格”档继续使用 `framemd5`，保证旧的像素完全一致语义不变。
- 其它等级通过 FFmpeg 输出标准化灰度 `rawvideo`，由 Node 与锚点比较。
- 左、右边界并行执行，避免串行等待。
- Stage A：指数级 Coarse Search。从锚点开始按 1s / 2s / 4s / 8s / 16s…向外探测，每个探测点只抽取 1 帧；第一次遇到“不相似”时得到“内侧相似点 + 外侧不相似点”的边界包围区间。若一直相似到文件首尾，则直接使用媒体边缘。
- Stage B：Binary Boundary Search。对 Stage A 的包围区间反复二分，只抽取中点单帧，直到边界窗口收敛到 0.75 秒以内。
- Stage C：Frame-level Refinement。仅对收敛后的边界附近增加约 0.35 秒上下文，并以 30 FPS 输出 160×90 灰度帧逐帧比较；最终边界精度约 33ms。
- 相似度探测结果按时间点缓存，二分阶段不会重复解码同一个探测点。
- 与旧版“每 30 秒整块、30 FPS 一路线性扫描到边界”相比，长静止区间不再需要把中间几小时的每一帧都送到 Node 比较；主要成本变为少量随机 seek + 最终边界附近逐帧精修。
- 二进制 FFmpeg 输出统一通过 ProcessRunner 的 `runProcessBinary` 执行，保持 `shell:false` 与取消控制。

父区间确定后，若存在音轨：

- 使用 `silencedetect=noise=-40dB:d=0.25` 检测静音段。
- 将父区间完整切分为交替的“有背景声音 / 无背景声音”子区间。
- “有背景声音”实际表示检测到非静音音频能量，不区分对白、音乐或环境声来源。
- 无音轨视频的整个父区间视为“无背景声音”。

真实基准文件 `C:\Users\asus\Desktop\hxsd-一阶段\0121-1.mp4`，锚点 14700 秒：

- 严格：0.033 秒，约 1.709 秒完成。
- 极低：1.933 秒，约 1.278 秒完成。
- 低：3.067 秒，约 1.264 秒完成。
- 标准：9.900 秒，约 1.230 秒完成。
- 宽松：13.933 秒，约 1.292 秒完成。
- 很宽松：85.933 秒，约 2.136 秒完成。

默认等级为“标准”。

- “很宽松 · 0.10%”父区间：27588.644 → 34828.822 秒，持续约 7240.179 秒（约 2 小时 0 分 40 秒）。

#### 查找结果进入统一历史结果池

方向检测、相似定位和人工 In/Out 现在统一进入同一个 `FreezeInterval[]` 结果池：

1. 每次方向检测都会创建独立 `SearchRun`，保存查找批次、锚点时间、方向、音频条件和结果数量。
2. 新的方向检测结果采用 append 方式加入结果池，不再清除之前的 `source: 'detected'` 结果。
3. 每次相似定位成功后也立即生成一个未勾选的 `source: 'similarity'` 候选并保留查找批次；“加入待删除”只切换该历史候选的 `selectedForRemoval`。
4. 人工 In/Out 区间继续直接进入统一结果池，标记 `source: 'manual'`。
5. 每个方向检测/相似定位批次都生成唯一的 `searchRunId`，最终候选 ID 也包含 run ID，避免不同查找批次的 `freeze-0001` 等本地编号互相冲突。
6. UI 的“删除时长 / 预计输出时长”仍按所有已选区间的时间并集计算，重叠区间不会重复计时。
7. 导出前同样先合并重叠/相邻删除范围，再交给现有 Export Planner，因此不同查找批次或不同来源区间重叠时不会重复裁剪。
8. 所有查找和勾选操作只改变当前编辑计划，不修改源文件；真正的视频修改仍只发生在用户主动执行“导出视频”之后。

### 8.5 Parser 状态机

FFmpeg 输出可能是：

```text
freeze_start: 12.400
freeze_duration: 5.800
freeze_end: 18.200
```

Parser 内部维护：

```ts
interface PendingFreeze {
  startSec?: number;
  durationSec?: number;
}
```

规则：

1. 收到 freeze_start -> 创建 pending。
2. 收到 freeze_duration -> 更新 pending duration。
3. 收到 freeze_end -> 生成完整区间。
4. start/end 必须有限数值且 end > start。
5. duration 最终统一使用 `end - start`，避免日志舍入误差。
6. 若文件结束时存在只有 start 无 end 的冻结区间，则用媒体 duration 作为 end。
7. 输出前按 start 排序并去重。

### 8.6 正则

```ts
const startRe = /lavfi\.freezedetect\.freeze_start:\s*([0-9.]+)/;
const durationRe = /lavfi\.freezedetect\.freeze_duration:\s*([0-9.]+)/;
const endRe = /lavfi\.freezedetect\.freeze_end:\s*([0-9.]+)/;
```

## 10. 区间管理与统一筛选

所有历史候选先进入完整结果池 `intervals`，再由 `IntervalFilterState` 派生 `visibleIntervals`。列表和 Timeline 都只渲染 `visibleIntervals`，但最终导出仍读取完整结果池中所有 `selectedForRemoval=true` 的区间。

### 10.1 来源与查找批次

顶部来源 Tab：

- 全部区间
- 方向检测
- 相似定位
- 人工指定

每个 Tab 显示该来源在完整结果池中的总数。

“查找批次”下拉框可进一步只查看某一次方向检测或相似定位。每个 `SearchRun` 保存：

- `id`
- `source`
- `label`
- `createdAt`
- `resultCount`
- `anchorSec`
- 方向检测专用的 `direction` / `hasBackgroundSound`

候选行会显示来源标签，以及类似“方向检测 #2 · 锚点 05:15:45.373”的批次信息。

### 10.2 筛选条件

当前支持：

- 来源类型
- 查找批次
- 最小时长
- 最大时长
- 时间范围起点 / 终点
- 方向检测音频条件：全部 / 允许背景声音 / 要求无背景声音
- 仅显示已勾选区间

筛选条件是非破坏性的，只控制当前可见结果；“重置筛选”恢复全部来源、全部批次和整段时间范围。

### 10.3 批量操作

批量操作只作用于当前 `visibleIntervals`：

- “全选当前结果”：只切换当前筛选出来的候选，不修改隐藏候选。
- “删除所选区间”：只从当前筛选结果中删除已勾选候选。
- “设为不删除”：只取消当前筛选结果中的删除勾选。
- 单条候选右侧也提供独立删除按钮。

删除候选后，Timeline 标记、删除总时长、预计输出时长和导出 RemoveRanges 都由同一结果池状态自动同步。若被删除候选正处于 active/区间自动预览状态，同时清除 active 和 preview end。

### 10.4 排序与显示

当前可见候选固定按 `startSec` 升序显示；同一起点再按 `endSec` 排序。筛选结果统计同时显示“当前显示 X / 总计 Y 段”和累计查找次数。

## 11. 预览算法

候选列表预览采用“真实起点 + 0.5 秒尾部上下文”，不再向前预滚 0.5 秒：

```ts
previewStart = interval.startSec;
previewEnd = Math.min(mediaDuration, interval.endSec + 0.5);
```

这样点击方向检测/相似定位/人工候选的预览按钮后，播放器第一帧就是候选真实起点，避免把起点前的镜头跳变误认为静止区间内容。其它需要观察上下文的父区间/音频子区间预览仍可显式使用 lead 上下文。

预览流程：

1. 候选列表预览将播放器 `currentTime` 直接设为 `interval.startSec`。
2. play。
3. `timeupdate` 时若 `currentTime >= interval.endSec + 0.5`，自动 pause。
4. 用户主动拖动后退出“区间自动预览模式”。

## 12. Unified Timeline

主播放器关闭 Chromium 原生 `controls`，由应用自绘一条统一进度时间轴，避免原生进度条与候选时间轴重复出现。这样候选区间、播放进度、拖动定位和画面预览都在同一条时间轴上完成。

位置计算：

```ts
leftPct = startSec / durationSec * 100;
widthPct = (endSec - startSec) / durationSec * 100;
playheadPct = currentTimeSec / durationSec * 100;
```

视觉状态：

- detected：方向检测候选，绿色。
- similarity：当前画面相似定位候选，蓝色。
- manual：人工 In/Out 区间，橙色。
- selected：待删除区间，红色覆盖来源颜色。
- active：当前正在查看的区间。
- played：当前播放进度底色。
- playhead：播放器当前时间。

统一时间轴支持：

- 单击任意位置直接 seek，时间只由鼠标横向位置决定。
- 候选色块是纯视觉标记（`pointer-events:none`），不会拦截点击；即使点击点落在候选区间内部，也跳转到鼠标所在时间，而不是候选起点。
- 按住左键拖动连续 seek，跨过候选色块时行为保持一致。
- 鼠标悬停显示共享画面预览。
- 候选区间的整段预览继续通过右侧候选列表触发，避免和时间轴精确定位语义冲突。
- 时间轴上方控制条提供播放/暂停、向左一帧、向右一帧、In/Out 设置。

### 12.1 鼠标悬停画面预览

统一时间轴根据鼠标横向位置换算对应的 `hoverTimeSec`：

- 显示 224×126 的浮动画面卡片，并同时显示精确时间。
- 卡片横向跟随鼠标，但在左右边缘按卡片半宽做 clamp。
- 只使用一个只读 `<video>` 预览实例，避免 decoder / media buffer 竞争。
- 预览 video 使用 `preload="metadata"`、`muted`，不自动播放，只通过修改 `currentTime` 取得对应帧。
- 鼠标位置和时间标签每次 `mousemove` 立即更新，但实际媒体 seek 使用约 45ms throttle。
- 同一时刻最多只允许一个 seek 在执行；新鼠标位置只覆盖 `latestTarget`，不会中断当前 in-flight seek。
- 当前 seek 完成后，如果 `latestTarget` 已变化，直接 seek 到最新目标（latest-wins）。
- 鼠标停止后约 110ms 再执行一次 final settle，确保最终画面与最终鼠标位置一致。
- 预览不会修改主播放器播放/暂停状态。
- 不预生成全片缩略图，超长文件继续依赖 HTTP Byte Range 随机读取。
- `app-media://` Range 响应允许 5 分钟私有缓存，并返回 `ETag` / `Last-Modified`。

### 12.2 单帧步进

单帧步进使用 ffprobe 得到的媒体 FPS，而不是固定写死 30fps：

```ts
currentFrame = round(currentTimeSec * fps)
targetFrame = currentFrame + direction
targetTimeSec = targetFrame / fps
```

- 向左一帧 / 向右一帧都会先暂停播放。
- 目标帧 clamp 到 `0..floor(durationSec * fps)`。
- 步进后清除区间自动预览和旧的相似定位结果，确保后续按 I/O 设置的是当前精确位置。
- 对 30fps 视频，每次步进约为 33.333ms。

## 13. 区间标准化

导出之前执行：

```ts
normalizeRemoveRanges(ranges, duration)
```

步骤：

1. 过滤非法数值。
2. clamp 至 0..duration。
3. 删除 `end <= start`。
4. 按 start 排序。
5. 对重叠区间和小于 epsilon 的相邻区间合并。

epsilon 建议：`0.001s`。

示例：

```text
[12.4,18.2]
[18.1999,20.0]
=> [12.4,20.0]
```

## 14. RemoveRanges -> KeepRanges

纯函数：

```ts
function buildKeepRanges(
  removeRanges: TimeRange[],
  duration: number
): TimeRange[]
```

伪代码：

```text
cursor = 0
for remove in normalizedRemoves:
    if remove.start > cursor:
        keep.push([cursor, remove.start])
    cursor = max(cursor, remove.end)

if cursor < duration:
    keep.push([cursor, duration])
```

要求单元测试覆盖：

- 无删除区间。
- 删除开头。
- 删除结尾。
- 删除中间。
- 多区间。
- 重叠区间。
- 相邻区间。
- 删除整个视频。
- 越界输入。

## 15. 长视频导出 Pipeline

### 15.1 策略选择顺序

`VideoExporter` 按以下顺序尝试导出：

1. `smart-copy`
2. `smart-render`
3. `reencode`

前一层只要发现不安全条件就返回 `false`，由下一层接管；取消操作仍直接抛出 `PROCESS_ABORTED`，不能被当成普通回退吞掉。

### 15.2 Keyframe-aware Smart Copy

适用条件：

- 视频编码为 H.264。
- 所有内部删除边界都能在容差范围内命中关键帧。
- FFmpeg 输出没有非单调 DTS、DTS out-of-order 或 packet corrupt。

实现：

- ffprobe 仅在切点附近小窗口探测关键帧，不扫描整片；多个内部切点按最多 4 路并行探测。
- 探测结果不仅用于判断 Smart Copy 是否可用，还保留每个切点命中的精确 keyframe 时间，Smart Copy 失败后交给 Smart Render 复用，避免同一边界再次重复 ffprobe。
- KeepRanges 写为 ffconcat 的同源多段 `file + inpoint + outpoint`。
- 最终 `-c copy`，音视频 packet 均不重新编码。

### 15.3 Frame-Accurate Smart Render：视频

当切点不在关键帧上时：

1. 优先复用 Smart Copy 已确认的 keyframe 切点；只有未知的 KeepRange 起点才继续 ffprobe 逐帧读取 `key_frame + best_effort_timestamp_time`。
2. 多个独立 KeepRange 的 frame probe 最多 4 路并行，同时保持原 KeepRange 顺序生成最终 plan。
3. 若起点就是关键帧，该 KeepRange 直接 copy。
4. 若起点位于 GOP 中间，只把 `range.start -> next keyframe` 这一小段用 libx264 重编码；多个独立边界段最多 2 路并行编码。
5. 从下一关键帧开始到 KeepRange 结束继续直接引用源 MP4 做 stream copy。
6. 边界编码段显式限制 `frames:v`，避免最后一帧与下一关键帧重复。
7. 当前检测到源视频存在 B-frame 时，为避免 DTS 重排序风险，Smart Render 暂不启用，直接进入全量回退。

边界编码尽量继承源视频 bitrate、pixel format、video track timescale 和 B-frame 参数，使重编码小段能够与源 packet 安全拼接。

### 15.4 Frame-Accurate Smart Render：音频

AAC 不能在任意样本点安全 `-c copy`；直接对多个 MP4 区间做 audio stream copy 会产生 edit-list / priming 导致的 DTS 回跳。因此音频独立重建：

1. 将所有 KeepRanges 进一步按 30 分钟切成 audio chunks。
2. 最多 4 个 FFmpeg 进程并行处理。
3. 每块使用输入侧精确 seek + `AAC 192k + aac_coder=fast` 编码到 MPEG-TS。
4. 每个 TS 块在 ffconcat 中同时写 `inpoint=0`、理论 `outpoint` 和理论 `duration`，裁掉 AAC 尾部 padding 对后续时间轴的影响。
5. concat 后只做 AAC copy + `aac_adtstoasc` 得到 M4A。
6. 不再先把视频 concat 计划物化成完整 `video.mp4`；最终 FFmpeg 直接读取 `smart-render.ffconcat` 作为视频输入、M4A 作为音频输入，通过 `-c copy` 一次写出最终 MP4。这样省掉一次完整视频写盘和一次再次读盘。

真实短样本中，理论 14.667 秒输出最终为约 14.680 秒，误差约 13ms，完整解码无 DTS/PTS 报错。

真实长视频基准 `C:\\Users\\asus\\Desktop\\hxsd-一阶段\\0122.mp4`：源时长 34845.333 秒（约 9:40:45），删除一个 995.123 → 1000.456 秒的非关键帧区间后，理论输出 34840.000 秒。旧版端到端约 5 分钟；完成并行 probe、关键帧结果复用、边界 GOP 并行编码和直接 concat+audio mux 后，实测 203.218 秒（约 3 分 23 秒），最终文件 6,523,687,018 bytes。实际视频时长仍为 34839.989667 秒，音频 34839.965667 秒，与旧版已验证结果完全一致；视频误差约 10ms、音视频尾部差约 24ms。对最终文件执行全片 `ffmpeg -v error -i output.mp4 -f null -`，exit code 0，零解码/DTS/PTS 错误。

同一真实源文件的 900 秒窗口，删除 599.123 → 604.456 秒后，Smart Render 约 9.741 秒完成；理论输出 894.667 秒，实际视频 894.656333 秒、音频 894.675000 秒，完整解码零错误。

### 15.5 Precise Reencode Fallback

以下任一情况触发全量回退：

- 非 H.264。
- Smart Render codec 参数不完整或含当前未支持的 B-frame。
- 找不到安全关键帧规划。
- 任一快速路径出现非单调 DTS、DTS out-of-order、packet corrupt。
- 临时输出为空。
- 最终输出时长与 KeepRanges 理论总时长漂移超过允许阈值。

回退继续使用原有：

```text
[0:v]trim=start=S0:end=E0,setpts=PTS-STARTPTS[v0];
[0:a]atrim=start=S0:end=E0,asetpts=PTS-STARTPTS[a0];
...
[v0][a0][v1][a1]...concat=n=N:v=1:a=1[outv][outa]
```

视频 `libx264 / CRF 18 / preset medium`，音频 AAC 192k；无音轨时只构建视频链。

## 16. 导出进度

FFmpeg 使用：

```text

-nostats
```

解析：

- `out_time_us`
- `out_time_ms`
- `progress=continue`
- `progress=end`

注意输出视频时长是 KeepRanges 总和，而不是源视频总时长。

## 20. 视频播放器

使用 HTML5 `<video>`。

本地文件 URL 由 Electron 安全转换或通过受控自定义 protocol 提供。

MVP 必须验证：

- H.264/AAC MP4。
- H.264 无音频 MP4。
- 超大/超长 MP4 的本地协议必须支持标准 HTTP Byte Range：返回 `206 Partial Content`、`Content-Range`、`Content-Length` 和 `Accept-Ranges: bytes`，保证播放器可随机 seek。
- 用户手动拖动播放器时间轴时，应退出“区间自动预览”模式，避免旧 previewEnd 继续控制暂停。
- 播放器提供“◀ 区间 / 区间 ▶”两个区域跳转按钮，基于当前筛选后的 `visibleIntervals` 工作。
- 导航区域由候选区间和两个候选区间之间的 gap 交替组成；重叠/相邻候选先通过 `mergeTimeRanges` 合并，避免历史重复结果制造虚假 gap。
- 若播放头位于候选区间内：左 → 当前区间开始；再次左 → 前一个 gap 开始。右 → 当前区间结束；再次右 → 后一个 gap 结束。
- 若播放头位于两个候选之间的 gap 内：左 → 当前 gap 开始；再次左 → 前一区间开始。右 → 当前 gap 结束；再次右 → 后一区间结束。
- gap 开始不是直接取前一区间的 `endSec`，而是 `endSec + 1/fps`，即前一区间结束后的下一帧；gap 结束为 `next.startSec - 1/fps`，即后一区间开始前的上一帧。
- 若当前筛选后没有任何可见区间：左 → 时间轴开始 `0`；右 → `media.durationSec`。
- 首个可见区间之前和最后一个可见区间之后也正式建模为 gap 区域，不再有首尾特殊跳过逻辑：最左 gap 为 `0 → first.startSec - 1/fps`，最右 gap 为 `last.endSec + 1/fps → media.durationSec`，同样遵循“当前区域边界优先、再进入相邻区域边界”的统一规则。
- 区间跳转使用约半帧的 epsilon 判断“已经位于该边界”，防止 seek 后浮点误差导致连续点击仍停留在同一边界。
- 区间跳转会暂停播放器，确保用户可以稳定检查边界并连续执行下一次跳转。
- HEVC 若 Chromium 当前环境不可播放，要给出明确提示，而不是把文件错误归因为损坏。

导出层 FFmpeg 可以支持更多 codec，但预览能力受 Chromium 解码支持影响。

### 20.1 工作区滚动布局

主窗口采用固定视口布局，避免大量静止区间把整页撑高：

- 应用根节点固定为当前窗口高度（`100vh`），禁止 body 整页纵向滚动。
- 顶部标题/操作区保持固定高度。
- 下方 workspace 占据剩余可视高度。
- 左侧播放器区域始终保持 workspace 高度，不随右侧静止区间数量变化。
- 右侧媒体信息 + 静止区间区域独立使用 `overflow-y: auto`。
- 右侧滚动时，左侧视频、播放器状态、时间轴和删除统计保持原位。

## 21. 人工指定删除区间

播放器下方提供人工 In/Out 标记工具：

- 点击“设置起点”或按 `I`，记录播放器当前时间为区间起点。
- 移动播放器后点击“设置终点”或按 `O`，以当前时间作为区间终点并立即生成 `source=manual` 的删除候选。
- 人工区间默认 `selectedForRemoval=true`，直接计入删除统计和导出 RemoveRanges。
- 重复按 `I` 会更新尚未完成的起点；`O` 早于或等于起点时拒绝创建并提示用户。
- 快捷键在 input / textarea / select / contenteditable 获得焦点时不触发，且不拦截 Ctrl/Meta/Alt 组合键。
- 重新执行方向检测不会替换任何已有候选，而是创建新的 `SearchRun` 并追加结果；`source=manual`、`source=similarity` 和之前的 `source=detected` 都继续保留。
- 人工区间与其他来源区间在导出前继续经过统一的 `mergeTimeRanges` 合并，重叠区间不会重复计算或重复裁切。

## 23. 重复查找与失败保护

1. 当前分析执行期间禁用同类启动按钮，避免重复并发提交。
2. 新查找开始时只清空 active preview，不清空历史结果。
3. 新查找成功后创建独立 `SearchRun` 并 append 新候选；旧候选及其勾选状态保持不变。
4. 新查找失败时只更新错误状态，不删除之前已经成功得到的任何候选。
5. 用户可通过来源 Tab、查找批次、时长、时间范围和音频条件筛选历史结果，而不是通过“重跑并覆盖”管理结果。

## 29. 长视频导出优化：Stage 2 Keyframe-aware Smart Copy

针对 8 小时以上长视频，原 trim/atrim + concat + libx264 会对全部保留内容重新编码，导出耗时与保留时长近似线性增长。Stage 2 新增安全 Smart Copy 路径：

1. ExportRequest 额外携带 fps、videoCodec、audioCodec。
2. 导出前对所有内部删除边界做定向关键帧探测；ffprobe 仅读取边界前后约 12 秒窗口，不扫描全片。
3. 当前仅 H.264 启用 Smart Copy。
4. 所有删除边界都在约半帧容差内命中关键帧时，生成 ffconcat 计划，同一个源文件按多个 inpoint/outpoint 直接参与 concat。
5. FFmpeg 使用 -c copy 输出，不产生中间媒体片段，不重新编码视频。
6. 任一边界不安全、探测失败或 Smart Copy FFmpeg 执行失败时，自动回退原有精确重编码路径；取消任务不会触发回退。
7. ExportProgress / ExportFinished 增加 strategy：smart-copy | smart-render | reencode，便于后续 UI 与诊断。
8. 临时 concat 计划与失败输出均自动清理。

真实验证文件：C:\\Users\\asus\\Desktop\\hxsd-一阶段\\0122.mp4。以源文件前 900 秒为验证窗口，删除关键帧对齐区间 599.3333→604.3333 秒，实际输出 895.000 秒，H.264/AAC 完整解码无错误；实际 VideoExporter 命中 smart-copy，导出约 1.553 秒。

Stage 2 的限制是：普通检测得到的切点通常不刚好位于关键帧，因此不能覆盖全部场景。下一阶段使用 Frame-Accurate Smart Render，只对切点附近 GOP 重编码，中间长区间继续原码复制。
