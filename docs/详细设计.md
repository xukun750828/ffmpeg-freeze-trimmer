## 7. MediaProbe 详细设计

命令：

```bash
ffprobe -v error -print_format json -show_format -show_streams input.mp4
```

解析规则：

- duration 优先 `format.duration`。
- 找第一条 `codec_type=video` 的 stream。
- 音频存在任意 `codec_type=audio` 即 `hasAudio=true`。
- fps 从 `avg_frame_rate` 解析；若无效再尝试 `r_frame_rate`。
- duration 必须 > 0。

错误条件：

- ffprobe 非 0。
- JSON 无法解析。
- 无 video stream。
- duration 非法。

### 8.2 长视频自适应检测

30 秒以上视频不再对整段原始帧流直接执行完整 `freezedetect`，而是采用两阶段策略：

1. 快速粗扫：缩放到 360p，并根据最短静止时长动态选择 1–8 FPS；默认 2 秒阈值使用 2 FPS。
2. 原分辨率精修：粗扫只产生候选，最终边界仍回到原分辨率确认。

为降低候选密集型超长视频的精修成本：

- 每个候选只生成“开始边界窗口”和“结束边界窗口”，不会重新解码整个静止段。
- 相邻/重叠边界窗口会自动合并，单个合并窗口最长 12 秒，避免合并过大导致重新大量解码。
- 合并后的精修窗口最多 4 路并行执行。
- 同一候选至少有一个边界必须被原分辨率检测确认，否则视为粗扫假阳性并丢弃。
- 精确边界采用一对一匹配，同一个原分辨率边界不会同时确认多个相邻粗候选。
- 精修后若区间发生真实重叠，则合并去重；仅首尾相接但不重叠的独立区间保持分离。
- 共享同一个 AbortSignal；取消检测时所有正在运行的精修进程会一起终止。
- 真实基准 `0121-1.mp4`：优化前 755.139 秒；合并窗口 + 4 路并行 + 匹配保护后 315.879 秒，约缩短 58%。

实测基准文件 `C:\Users\asus\Desktop\hxsd-一阶段\0121-1.mp4`（约 5.32 GB、8:22:20、1080p、约 30 FPS）用于长期性能回归。

### 8.3 手动定向检测

导入 MP4 后不再自动启动静止检测。播放器只负责加载媒体并显示当前时间点，用户完成参数设置后手动点击“启动检测”。

检测请求包含：

- 当前播放器时间 `currentTimeSec`
- 检测方向：`forward` / `backward`
- 最大返回区间数量 `maxIntervals`
- 最短静止时长
- 允许画面变化阈值
- 是否有背景声音
- 视频是否存在音轨

定向搜索采用分块策略：

1. 从当前时间点开始，每次扫描最多 300 秒。
2. 向后检测时，按时间增加方向继续扫描；向前检测时，按时间减少方向扫描。
3. 每个块仍使用“低 FPS / 360p 粗扫 + 原分辨率边界精修”。
4. 找到用户指定数量后立即停止，不继续扫描剩余视频。
5. 相邻块保留少量重叠上下文，避免静止区间刚好跨块时被错误截断。
6. 对触及尚未扫描边界的候选，延迟到下一重叠块确认，防止把块边界当成真实 freeze_end / freeze_start。

背景声音规则：

- “有背景声音”开启：静止判断只看画面，不要求音频静默。
- “有背景声音”关闭且视频存在音轨：使用 `silencedetect=noise=-35dB` 做辅助确认，静止区间还必须满足足够的静音重叠。
- 无音轨视频：无论该开关状态如何，都只按画面判断。

真实基准 `C:\Users\asus\Desktop\hxsd-一阶段\0121-1.mp4`：
从 04:00:00 开始向后查找 3 个静止区间，完成时间约 4.731 秒。

### 8.4 当前画面相似定位

该功能与“方向查找静止区间”并行存在，不替代原有快速检测。

目标：以播放器当前时间点对应的画面作为锚点，允许用户配置画面变化等级，然后向左右定位持续满足该等级的最大连续父区间。

变化等级：

| 等级 | 最大标准化平均像素差 | 用途 |
| --- | ---: | --- |
| 严格 | 0% | 原始解码像素完全一致，保留旧 MD5 行为 |
| 极低 | 0.005% | 只容忍极轻微压缩抖动 |
| 低 | 0.02% | 容忍少量编码噪声 |
| 标准 | 0.05% | 默认，兼顾稳定性和实用区间长度 |
| 宽松 | 0.08% | 允许更明显的小范围画面变化 |
| 很宽松 | 0.10% | 适合压缩噪声大或缓慢变化的素材 |

“标准化平均像素差”计算方式：

1. 当前锚点帧和待比较帧统一缩放到 160×90。
2. 转为 8-bit 灰度图。
3. 对每个像素计算绝对差。
4. 使用 `sum(abs(anchor - frame)) / (pixelCount * 255)` 得到 0～1 的差异值。
5. 差异值不超过当前等级阈值即认为该帧与当前画面相似。

实现策略：

- “严格”档继续使用 `framemd5`，保证旧的像素完全一致语义不变。
- 其它等级通过 FFmpeg 输出标准化灰度 `rawvideo`，由 Node 与锚点比较。
- 左、右边界并行执行，避免串行等待。
- Stage A：指数级 Coarse Search。从锚点开始按 1s / 2s / 4s / 8s / 16s…向外探测，每个探测点只抽取 1 帧；第一次遇到“不相似”时得到“内侧相似点 + 外侧不相似点”的边界包围区间。若一直相似到文件首尾，则直接使用媒体边缘。
- Stage B：Binary Boundary Search。对 Stage A 的包围区间反复二分，只抽取中点单帧，直到边界窗口收敛到 0.75 秒以内。
- Stage C：Frame-level Refinement。仅对收敛后的边界附近增加约 0.35 秒上下文，并以 30 FPS 输出 160×90 灰度帧逐帧比较；最终边界精度约 33ms。
- 相似度探测结果按时间点缓存，二分阶段不会重复解码同一个探测点。
- 与旧版“每 30 秒整块、30 FPS 一路线性扫描到边界”相比，长静止区间不再需要把中间几小时的每一帧都送到 Node 比较；主要成本变为少量随机 seek + 最终边界附近逐帧精修。
- 二进制 FFmpeg 输出统一通过 ProcessRunner 的 `runProcessBinary` 执行，保持 `shell:false` 与取消控制。

父区间确定后，若存在音轨：

- 使用 `silencedetect=noise=-40dB:d=0.25` 检测静音段。
- 将父区间完整切分为交替的“有背景声音 / 无背景声音”子区间。
- “有背景声音”实际表示检测到非静音音频能量，不区分对白、音乐或环境声来源。
- 无音轨视频的整个父区间视为“无背景声音”。

真实基准文件 `C:\Users\asus\Desktop\hxsd-一阶段\0121-1.mp4`，锚点 14700 秒：

- 严格：0.033 秒，约 1.709 秒完成。
- 极低：1.933 秒，约 1.278 秒完成。
- 低：3.067 秒，约 1.264 秒完成。
- 标准：9.900 秒，约 1.230 秒完成。
- 宽松：13.933 秒，约 1.292 秒完成。
- 很宽松：85.933 秒，约 2.136 秒完成。

默认等级为“标准”。

#### 相似定位结果进入删除链路

相似定位得到的父区间可以直接加入现有“待删除”工作流：

1. 定位完成后，父区间旁显示“加入待删除”按钮；再次点击可取消删除。
2. 相似定位父区间转换为统一的 `FreezeInterval` 候选，并标记 `source: 'similarity'`；方向检测结果标记 `source: 'detected'`。
3. 相似定位候选与方向检测候选统一显示在“删除候选区间”列表和时间轴中，但保留来源标签。
4. 重新执行方向检测时，只替换 `detected` 候选，不清除已经加入的 `similarity` 候选。
5. 多个相似定位结果可以累计加入待删除；用户可通过候选列表复选框逐个取消或重新选择。
6. UI 的“删除时长 / 预计输出时长”按所有已选区间的时间并集计算，重叠区间不会重复计时。
7. 导出前同样先合并重叠/相邻删除范围，再交给现有 Export Planner，因此相似定位与方向检测区间重叠时不会重复裁剪。
8. “加入待删除”只改变当前编辑计划，不修改源文件；真正的视频修改仍只发生在用户主动执行“导出视频”之后。

### 8.5 Parser 状态机

FFmpeg 输出可能是：

```text
freeze_start: 12.400
freeze_duration: 5.800
freeze_end: 18.200
```

Parser 内部维护：

```ts
interface PendingFreeze {
  startSec?: number;
  durationSec?: number;
}
```

规则：

1. 收到 freeze_start -> 创建 pending。
2. 收到 freeze_duration -> 更新 pending duration。
3. 收到 freeze_end -> 生成完整区间。
4. start/end 必须有限数值且 end > start。
5. duration 最终统一使用 `end - start`，避免日志舍入误差。
6. 若文件结束时存在只有 start 无 end 的冻结区间，则用媒体 duration 作为 end。
7. 输出前按 start 排序并去重。

### 8.6 正则

```ts
const startRe = /lavfi\.freezedetect\.freeze_start:\s*([0-9.]+)/;
const durationRe = /lavfi\.freezedetect\.freeze_duration:\s*([0-9.]+)/;
const endRe = /lavfi\.freezedetect\.freeze_end:\s*([0-9.]+)/;
```

## 11. 预览算法

```ts
function getPreviewWindow(
  interval: TimeRange,
  mediaDuration: number,
  lead = 0.5,
  tail = 0.5
) {
  return {
    startSec: Math.max(0, interval.startSec - lead),
    endSec: Math.min(mediaDuration, interval.endSec + tail),
  };
}
```

预览流程：

1. 设置播放器 currentTime 为 preview.startSec。
2. play。
3. timeupdate 时若 `currentTime >= preview.endSec`，自动 pause。
4. 用户主动拖动后退出“区间自动预览模式”。

### 12.1 鼠标悬停画面预览

界面存在两条可交互时间轴：

1. 主播放器 Chromium `<video controls>` 自带的原生进度条；
2. 播放器下方应用自绘的 Timeline。

两条时间轴都支持同样的鼠标跟随画面预览：

- 根据鼠标横向位置换算对应的 `hoverTimeSec`。
- 显示 224×126 的浮动画面卡片，并同时显示精确时间。
- 卡片横向跟随鼠标，但在左右边缘按卡片半宽做 clamp。
- 上、下两条时间轴共享同一个只读 `<video>` 预览实例，避免两个 decoder / media buffer 竞争。
- 预览 video 使用 `preload="metadata"`、`muted`，不自动播放，只通过修改 `currentTime` 取得对应帧。
- 鼠标位置和时间标签每次 `mousemove` 立即更新，但实际媒体 seek 使用约 45ms throttle。
- 同一时刻最多只允许一个 seek 在执行；新鼠标位置只覆盖 `latestTarget`，不会中断当前 in-flight seek。
- 当前 seek 完成后，如果 `latestTarget` 已变化，立即跳过所有中间目标并直接 seek 到最新目标（latest-wins）。
- 鼠标停止后约 110ms 再执行一次 final settle，确保最终画面与最终鼠标位置一致。
- 预览 video 常驻 DOM，鼠标离开时只隐藏浮层，不销毁媒体实例。
- 悬停预览不会修改主播放器 `currentTime`、播放/暂停状态或当前静止区间预览状态。
- 不预生成全片缩略图，超长文件继续依赖 HTTP Byte Range 随机读取，因此导入时没有新增预处理等待。
- `app-media://` Range 响应允许 5 分钟私有缓存，并返回 `ETag` / `Last-Modified`，让 Chromium 有机会复用已读取的 Range。

原生进度条实现说明：

- Chromium 原生 controls 位于 video 的 UA shadow tree，不能直接向其中注入 React 组件。
- 外层 `.video-stage` 监听真实 `mousemove`，只在距视频底部约 10～38px、左右各约 28px 的原生进度条带状区域显示预览。
- 浮层本身 `pointer-events:none`，所以不会挡住 Chromium 原生进度条的点击、拖拽、播放、音量等 controls。
- Electron 真实窗口验证中，系统级鼠标移动到原生 controls 进度条位置后，外层监听成功收到 `mousemove`，事件目标为 `VIDEO`。

真实文件 `C:\Users\asus\Desktop\hxsd-一阶段\0121-1.mp4` 验证：

- 主播放器固定在 120 秒时，独立悬停预览播放器可直接 seek 到 14400 秒（04:00:00），两者均为 `readyState=4`，主播放器位置保持不变。
- Chromium 原生进度条位置的真实鼠标事件可被 `.video-stage` 收到，因此上、下两条时间轴都能触发画面预览。

## 13. 区间标准化

导出之前执行：

```ts
normalizeRemoveRanges(ranges, duration)
```

步骤：

1. 过滤非法数值。
2. clamp 至 0..duration。
3. 删除 `end <= start`。
4. 按 start 排序。
5. 对重叠区间和小于 epsilon 的相邻区间合并。

epsilon 建议：`0.001s`。

示例：

```text
[12.4,18.2]
[18.1999,20.0]
=> [12.4,20.0]
```

## 14. RemoveRanges -> KeepRanges

纯函数：

```ts
function buildKeepRanges(
  removeRanges: TimeRange[],
  duration: number
): TimeRange[]
```

伪代码：

```text
cursor = 0
for remove in normalizedRemoves:
    if remove.start > cursor:
        keep.push([cursor, remove.start])
    cursor = max(cursor, remove.end)

if cursor < duration:
    keep.push([cursor, duration])
```

要求单元测试覆盖：

- 无删除区间。

## 15. 长视频导出 Pipeline

### 15.1 策略选择顺序

`VideoExporter` 按以下顺序尝试导出：

1. `smart-copy`
2. `smart-render`
3. `reencode`

前一层只要发现不安全条件就返回 `false`，由下一层接管；取消操作仍直接抛出 `PROCESS_ABORTED`，不能被当成普通回退吞掉。

### 15.2 Keyframe-aware Smart Copy

适用条件：

- 视频编码为 H.264。
- 所有内部删除边界都能在容差范围内命中关键帧。
- FFmpeg 输出没有非单调 DTS、DTS out-of-order 或 packet corrupt。

实现：

- ffprobe 仅在切点附近小窗口探测关键帧，不扫描整片。
- KeepRanges 写为 ffconcat 的同源多段 `file + inpoint + outpoint`。
- 最终 `-c copy`，音视频 packet 均不重新编码。

### 15.3 Frame-Accurate Smart Render：视频

当切点不在关键帧上时：

1. ffprobe 在 KeepRange 起点附近读取逐帧 `key_frame + best_effort_timestamp_time`。
2. 若起点就是关键帧，该 KeepRange 直接 copy。
3. 若起点位于 GOP 中间，只把 `range.start -> next keyframe` 这一小段用 libx264 重编码。
4. 从下一关键帧开始到 KeepRange 结束继续直接引用源 MP4 做 stream copy。
5. 边界编码段显式限制 `frames:v`，避免最后一帧与下一关键帧重复。
6. 当前检测到源视频存在 B-frame 时，为避免 DTS 重排序风险，Smart Render 暂不启用，直接进入全量回退。

边界编码尽量继承源视频 bitrate、pixel format、video track timescale 和 B-frame 参数，使重编码小段能够与源 packet 安全拼接。

### 15.4 Frame-Accurate Smart Render：音频

AAC 不能在任意样本点安全 `-c copy`；直接对多个 MP4 区间做 audio stream copy 会产生 edit-list / priming 导致的 DTS 回跳。因此音频独立重建：

1. 将所有 KeepRanges 进一步按 30 分钟切成 audio chunks。
2. 最多 4 个 FFmpeg 进程并行处理。
3. 每块使用输入侧精确 seek + `AAC 192k + aac_coder=fast` 编码到 MPEG-TS。
4. 每个 TS 块在 ffconcat 中同时写 `inpoint=0`、理论 `outpoint` 和理论 `duration`，裁掉 AAC 尾部 padding 对后续时间轴的影响。
5. concat 后只做 AAC copy + `aac_adtstoasc` 得到 M4A。
6. 最后将 Smart Render 视频 MP4 与 M4A 使用 `-c copy` mux 成最终 MP4。

真实短样本中，理论 14.667 秒输出最终为约 14.680 秒，误差约 13ms，完整解码无 DTS/PTS 报错。

真实长视频基准 `C:\\Users\\asus\\Desktop\\hxsd-一阶段\\0122.mp4`：源时长 34845.333 秒（约 9:40:45），删除一个 995.123 → 1000.456 秒的非关键帧区间后，理论输出 34840.000 秒；实际视频时长 34839.989667 秒，误差约 10ms，音频时长 34839.965667 秒，与视频尾部差约 24ms。最终文件约 6.52GB，端到端导出约 5 分钟。对最终文件执行全片 `ffmpeg -v error -i output.mp4 -f null -` 解码校验，172.355 秒完成，exit code 0，零解码/DTS/PTS 错误。

### 15.5 Precise Reencode Fallback

以下任一情况触发全量回退：

- 非 H.264。
- Smart Render codec 参数不完整或含当前未支持的 B-frame。
- 找不到安全关键帧规划。
- 任一快速路径出现非单调 DTS、DTS out-of-order、packet corrupt。
- 临时输出为空。
- 最终输出时长与 KeepRanges 理论总时长漂移超过允许阈值。

回退继续使用原有：

```text
[0:v]trim=start=S0:end=E0,setpts=PTS-STARTPTS[v0];
[0:a]atrim=start=S0:end=E0,asetpts=PTS-STARTPTS[a0];
...
[v0][a0][v1][a1]...concat=n=N:v=1:a=1[outv][outa]
```

视频 `libx264 / CRF 18 / preset medium`，音频 AAC 192k；无音轨时只构建视频链。

## 16. 导出进度

FFmpeg 使用：

```text
-progress pipe:1
-nostats
```

解析：

- `out_time_us`
- `out_time_ms`
- `progress=continue`
- `progress=end`

注意输出视频时长是 KeepRanges 总和，而不是源视频总时长。

普通 Smart Copy / Reencode 仍按 `outTimeSec / expectedDuration` 映射。Smart Render 为避免多阶段进度反复回跳，使用分段进度窗口：视频拼接约 0–15%，并行音频编码约 15–90%，音频 concat 约 90–95%，最终 A/V mux 约 95–99%，完成事件统一置 100%。

## 20. 视频播放器

使用 HTML5 `<video>`。

MVP 必须验证：

### 20.1 工作区滚动布局

主窗口采用固定视口布局，避免大量静止区间把整页撑高：

- 应用根节点固定为当前窗口高度（`100vh`），禁止 body 整页纵向滚动。
- 顶部标题/操作区保持固定高度。
- 下方 workspace 占据剩余可视高度。
- 左侧播放器区域始终保持 workspace 高度，不随右侧静止区间数量变化。
- 右侧媒体信息 + 静止区间区域独立使用 `overflow-y: auto`。
- 右侧滚动时，左侧视频、播放器状态、时间轴和删除统计保持原位。

## 28. 长视频导出优化：Stage 2 Keyframe-aware Smart Copy

针对 8 小时以上长视频，原 trim/atrim + concat + libx264 会对全部保留内容重新编码，导出耗时与保留时长近似线性增长。Stage 2 新增安全 Smart Copy 路径：

1. ExportRequest 额外携带 fps、videoCodec、audioCodec。
2. 导出前对所有内部删除边界做定向关键帧探测；ffprobe 仅读取边界前后约 12 秒窗口，不扫描全片。
3. 当前仅 H.264 启用 Smart Copy。
4. 所有删除边界都在约半帧容差内命中关键帧时，生成 ffconcat 计划，同一个源文件按多个 inpoint/outpoint 直接参与 concat。
5. FFmpeg 使用 -c copy 输出，不产生中间媒体片段，不重新编码视频。
6. 任一边界不安全、探测失败或 Smart Copy FFmpeg 执行失败时，自动回退原有精确重编码路径；取消任务不会触发回退。
7. ExportProgress / ExportFinished 增加 strategy：smart-copy | smart-render | reencode，便于后续 UI 与诊断。
8. 临时 concat 计划与失败输出均自动清理。

真实验证文件：C:\\Users\\asus\\Desktop\\hxsd-一阶段\\0122.mp4。以源文件前 900 秒为验证窗口，删除关键帧对齐区间 599.3333→604.3333 秒，实际输出 895.000 秒，H.264/AAC 完整解码无错误；实际 VideoExporter 命中 smart-copy，导出约 1.553 秒。

Stage 2 的限制是：普通检测得到的切点通常不刚好位于关键帧，因此不能覆盖全部场景。下一阶段使用 Frame-Accurate Smart Render，只对切点附近 GOP 重编码，中间长区间继续原码复制。
